**2. 重构待办的持久化方向（P0，已复现缺陷）**

当前链路是：浏览器 localStorage → 页面挂载或待办变化 → PUT 整份数组 → 覆盖服务端快照。页面没有先从服务端恢复待办，也没有并发版本检查。

隔离验证步骤与结果：

1. 启动同一份源码的独立 4184 端口服务，把 LOCALAPPDATA 指向临时目录。
2. 只向这个临时目录写入 1 条合成待办。
3. 使用新的浏览器 origin 打开首页，不进行任何待办编辑。
4. 隔离 API 中的待办由 1 条变成 0 条。
5. 复查正式 4173 API，仍是 7 条，syncedAt 仍为 2026-09-01T15:56:56.241Z。

这是正式提醒快照被空浏览器覆盖的缺陷，不等同于已经证明用户原浏览器的数据丢失。两个持有不同旧数据的标签页也存在互相覆盖风险。

建议由本机服务拥有待办的权威记录，浏览器先读取、后提交具体变更；提交携带 revision，并拒绝旧版本覆盖。保留变更记录、撤销和迁移前备份。localStorage 可继续保存尚未提交的输入草稿，但不应在页面加载时充当服务端的全量写入源。可以先改造现有文件存储，是否使用 SQLite 是下一步实现选择，不是解决问题的前提。

脚本聊天还以文件路径作为 localStorage 记录入口；后续统一会话持久化时，要让稿件移动或改名仍能找到原会话。

验收：新浏览器能读出既有待办；两个标签页编辑不会静默覆盖；失败保持可见；定时提醒能区分“确认没有待办”和“数据尚未同步”。

代码证据：[loadTodos / syncTodos](E:/projects/knowledgeProjects/DailyWrite/90-工具项目/dailywrite-workbench/src/todoStore.js:18)、[挂载同步](E:/projects/knowledgeProjects/DailyWrite/90-工具项目/dailywrite-workbench/src/App.jsx:978)、[服务端覆盖写入](E:/projects/knowledgeProjects/DailyWrite/90-工具项目/dailywrite-workbench/server/todoSnapshot.mjs:74)。

浏览器存储按 origin 隔离，见 [MDN localStorage](https://developer.mozilla.org/en-US/docs/Web/API/Window/localStorage)。版本条件写入可参考 [MDN If-Match](https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Headers/If-Match)，用于拒绝已过期版本的更新。

**3. 首页应该回答“今天推进什么”，并识别离发布最近的内容（P1）**

9 月 5 日首页仍推荐 DeepSeek Harness 8 月中旬稿。源码规则是“已登记、创作中、非空、最近修改”，却把结果称为“今天最值得继续推进的内容”。该规则能找最近改过的稿，不能判断时效、截止时间、商业价值、素材是否齐备或剩余工作量。

建议首页先展示你明确选定的本周交付和今日推进项，再参考截止时间、可用证据、阻塞和剩余动作。没有足够信息时提供候选及推荐理由，不编造精准分数。先检查已有成片和接近完成的稿件，再决定是否开新题。

内容过程需要能区分：选题、脚本、待录制、制作中、待发布、已发布与复盘。具体可以作为主状态的细分字段，避免未经讨论直接扩充所有目录或迁移文件。每条内容至少能说明：当前阶段、下一步、由谁做、卡在哪里、现有产物、预期交付时间。

首页的今日待办目前只看日期等于今天的记录，历史未完成事项不会进入该摘要。建议增加逾期与待验收入口。既有待办页的跨日期筛选是已确定的行为，可保留；不应为了首页调整而偷偷改掉它。

界面可收敛为“今日、内容、情报、资产、复盘”五个主要入口；这是待验证的信息组织建议。各类库仍可作为内部视图。首页弱化长 content_id、字节数和复制动作，把主题、阻塞和可执行下一步提到前面。

验收：不靠记忆找出待发布库存；打开首页能确定一个具体动作；“已拍好”不会仍被推荐去重新写稿。

**4. 从文件浏览切换到围绕 content_id 组织交付（P1）**

当前将主推加入待办，只把 content_id 写进标题，把下一步复制到 notes。待办本身没有结构化内容关联，任务完成也不会成为可检查的内容进展。

建议让一条内容聚合自己的来源、长稿、口播稿、封面、演示、成片、平台发布和复盘。它们是同一内容的产物或不同平台版本，而不是互不相识的文件。

待办关联 content_id；运行关联 todoId 与 runId；实际产物关联对应内容和任务。一条内容发布到抖音和小红书时，分别保留平台作品标识、实际发布文案和指标快照，避免把两个平台的数据合成一个含混的作品数字。

不需要立刻建立庞大知识图谱。先打通一条实际链路：读到情报 → 选择已有主题或新建主题 → 补实测待办 → Agent 产物 → 人工验收 → 发布记录 → 一条可复用经验。

**5. Agent 协作应围绕交付和验收（P1）**

当前已经有真实 Runtime、独立会话、取消、SSE 进度和最终结果。这些能力值得保留。缺口是用户还需要自己把任务定义、输出与文件变化组织成可验收的交付。

建议增加与你高频工作相符的任务入口：补来源事实、只改开头、生成分平台标题、转换提词稿、列实测录屏清单、做发布复盘。默认携带当前内容与已有素材，清楚显示本次输出和范围；Runtime 设置留在需要时展开的位置。

“程序运行成功”和“你接受结果”应分开。运行结束进入待验收，展示真实产物、关键文件差异、完成项及未完成项；接受后再更新待办或内容进度。AI 输出的一段成功说明不能代替产物检查。

技术上，待办和脚本台各自实现了运行观察与恢复。建议抽出共享逻辑，并把运行状态维护移出具体详情页：目前 Todo 的 RuntimeRunController 只挂在委派详情页，离开页面后这部分前端订阅会清理，不能把详情页是否打开作为全局状态及时性的前提。

创建任务遇到网络异常时，Todo 页对恢复列表失败使用 catch(() => [])，可能把“恢复查询也失败”折叠成“没有找到任务”。需要保留“结果未知”状态与错误链，使用稳定的客户端请求标识做幂等恢复。该项为源码审查发现，没有触发真实 Agent 来验证重复执行。

**6. 情报应产生可执行判断，复盘应产生可复用经验（P1）**

日报已做到多来源、日期档案与完整阅读。现在缺少从某个信号关联自己选题、实测和历史作品的直接动作。

建议在保留原文的基础上，增加单独的处理记录：与我哪条内容相关、是否有可拍案例、观众能拿走什么、值得实测还是略过。可以“关联内容 / 建立实测待办 / 稍后处理 / 已看过”，并保留来源与日期。相同话题被多个博主提到可作为需求信号，不应简单因为重复就排除；关键是你能否提供新的实际证明。

发布库当前 Excel 更新于本地时间 8 月 13 日，最新作品发布时间为 7 月 18 日。图表按作品发布日期汇总当前累计播放，因此“月度播放”不等同于“该月实际新增播放”。需要明确统计口径；要判断增量趋势，必须保留多个观测时间点。

3–5 分钟视频的当前均播比较只有 2 条样本，页面已显示样本数。它适合提出下一次实验，不能据此认定时长导致高播放。

分析记录的标识目前是 Excel 行号，没有 content_id 连接。建议先用显式映射连接平台作品和发布正文，未匹配项目单独列出，再让排行榜能打开真实稿件和复盘。不要把 147 条总记录与 22 条成品索引直接相减当作缺失作品数。

按你现有业务规划，复盘除播放、收藏、涨粉外，可先手动记录：是否带来有效咨询、客户提了什么问题、需求对应哪项服务。拿不到归因就标记未知，不自动推断成交。复盘只抽取证据充分的一两条经验，写回现有素材与方法论；优先处理有代表性的作品，不一次性补造 19 篇形式化复盘。

**7. 技术重构应服务上面的交付链路（P2，部分可靠性项提前）**

当前 App.jsx 为 1,276 行，TodoWorkspace.jsx 为 1,186 行，contentSnapshot.mjs 为 1,289 行，styles.css 为 6,344 行。问题不在行数本身，而是导航、数据、运行状态和多种业务视图的耦合。

实测快照 JSON 约 7.74 MB，作为 virtual:dailywrite-data 整体导入首页。日报占约 3.75 MB、周报约 1.81 MB、脚本库存约 1.06 MB；这些是序列化字节，不是压缩网络流量或首屏耗时。快照构建本次约 105 ms，健康请求约 204 ms，所以目前没有证据声称服务器扫描已经很慢。

建议先把“列表元数据”和“按需加载正文”分开，避免所有历史原文随首页导入；按内容、情报、待办、运行、分析拆分职责。保留当前 React 和 AppKit，逐块替换边界即可。

源码监控会对匹配的内容变化发送 full-reload，而导航由组件内 useState 保存。自动生成日报或 Agent 修改文件时，存在打断当前阅读/操作的机制风险。审查中曾出现页面回到首页，但未独立归因是哪一个文件变更；确定存在的代码路径应改为局部失效刷新，并持久化路由、选择与未提交草稿。

健康检查继续保持“坏的一条明确报错，其余可用内容继续工作”的隔离原则。新增独立的严格内容检查模式，让自动维护任务能据退出状态判断完整性；不要把日常服务存活检查改成一有旧稿断链就不停重启。

需同步消除权威规则冲突：根目录规则要求平台数据来自 04-数据与复盘/，并限定 03-已发布归档/ 只保存成品；工作台子目录规则与实际分析代码却从 03 根目录读取 Excel。应明确原始导入、指标权威层与索引的关系，再迁移和更新文档，不能默默维持两套口径。

**推荐实施顺序与验收**

| 顺序 | 交付 | 验收重点 |
|---|---|---|
| 第一批 | 待办权威存储与旧数据迁移；核对失效索引；拆开可用库存和异常记录 | 新浏览器不覆盖，旧标签页不静默覆盖，真实数据可追溯 |
| 第二批 | 选一条真实内容打通内容关联、下一步、Agent 产物与验收；改首页焦点来源 | 从已有内容推进到待发布，减少手工搬运，不误判完成 |
| 第三批 | 热点关联实测；平台作品映射；代表作复盘与经验写回 | 一条情报能追溯到内容，一条复盘能影响下一条作品 |
| 随对应模块推进 | 按需正文加载、稳定导航、共享运行管理、局部刷新 | 更新后台内容时不丢当前上下文；只加载当前需要的正文 |

改动前遵守项目规则创建重构分支，按业务边界逐批提交，不一次性搬完全部历史资产。第一批不依赖重新设计视觉风格，也不依赖引入新的 Agent 平台。

这轮完成的验证：现有测试 21/21 通过；validate:data 退出 0，但输出明确为 degraded，包含 17 项错误；正式健康 API 返回 HTTP 200、degraded=true；隔离环境复现首次打开覆盖待办；浏览器核对首页、热点、发布与脚本库。测试通过仅代表现有测试覆盖的行为通过，不代表上述产品闭环和数据完整性已经通过验收。

尚未验证：真实 Agent 提交/取消、跨浏览器并发写入的完整故障矩阵、移动端本轮表现、所有未登记文件的人工语义归类、实际咨询与成交归因。本次没有从旧记录推断这些结果。
