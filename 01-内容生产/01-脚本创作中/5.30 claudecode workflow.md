# Claude Code 的 Workflow 不是新命令，是 AI 编程开始变形的地方

事情是这样的。

今天我连着看了三份 Claude Code Workflow 的资料，看到后面有点兴奋，也有点背后发凉。

因为它不是又多了一个斜杠命令，不是又多了一个插件，也不是 Claude Code 又会了一个小技巧。

它更像是 Claude Code 正在从一个会写代码的助手，慢慢变成一个会自己组织工程队的人。

这个变化挺大的。

一开始我对 Workflow 这个词其实没啥感觉。

因为我们平时说工作流说太多了，什么内容工作流，剪辑工作流，开发工作流，听着就像一个更复杂的流程图。

但 Claude Code 这里的 Workflow，不太一样。

它不是让你提前画好一个流程，然后让 Claude Code 照着做。

它是你用自然语言说出目标之后，Claude Code 先给自己生成一段 JavaScript 脚本，把任务拆成阶段，把不同阶段分给不同 agent，再让 runtime 去执行这些 agent，再把结果收回来。

这一下味道就变了。

以前你是在跟一个模型聊天。

现在你是在让模型现场搭一个临时指挥系统。

![[5.30 claudecode workflow__assets/workflow-overview.png]]

资料里反复出现一个词，Harness Engineering。

这个词翻译起来有点别扭，你可以把它理解成给 agent 套上的工程轨道。

一个 agent 如果没有轨道，它就像一个聪明但容易兴奋的实习生，你交给它一个大任务，它可能会一口气往前冲，冲着冲着就偏了。

Harness 做的事，就是把它放进一个更可控的系统里。

什么时候搜索，什么时候分析，什么时候验证，什么时候汇总，什么时候停下来让人审。

这些都不是靠模型临场发挥，而是靠外面的结构来约束它。

以前这件事挺专业的。

你得会写 LangGraph、AutoGen、CrewAI 这一类框架，得懂多 agent 调度，得设计状态机，得处理上下文，得管 token，得想怎么验证。

说真的，这已经不是普通用户能玩的东西了。

但 Workflow 有意思的地方就在这里。

它把 Harness 从人手写，变成 Claude Code 根据任务现场生成。

你说你想做什么，它说行，我先写一个小型指挥系统。

然后它让几个 agent 并行去干活，有的负责扫代码，有的负责查 issue，有的负责验证，有的负责收口。

这就是我被打动的点。

不是模型更会说话了，是模型开始会给自己搭施工队了。

资料里有一个很夸张的例子，Bun 从 Zig 迁移到 Rust，75 万行代码，99.8% 通过率，11 天完成。

这个数字我没法替任何人背书，我只能说，它在资料里被拿来当 Dynamic Workflows 的代表案例。

但即使先不看这个结果，只看它背后的思路，也已经够值得聊了。

因为真正有意思的不是 75 万行，也不是 11 天。

真正有意思的是，它不是让一个 Opus 从头到尾硬扛。

它会拆。

它会让便宜模型做广度，让强模型做判断。

比如分类 GitHub Issues 的例子里，资料里提到的是 10 个 Haiku 4.5 去做广度分类，再让 1 个 Opus 4.8 做收口判断。

便宜模型干脏活，强模型做决策。

这就很像真实公司。

你不会让 CTO 一个人读完所有客服工单，也不会让实习生拍板架构方向。

你会让不同的人做不同层级的事。

AI 编程走到这一步，终于开始有一点组织结构的味道了。

以前我们总说 Claude Code 强，强在它能理解大项目，能改复杂代码，能跑测试，能自己调试。

但那仍然是一个强人模式。

像公司里有一个非常厉害的技术合伙人，你什么都找他，他也确实能扛。

Workflow 的变化是，它开始从强人模式变成组织模式。

一个人再强，也不如一套能分工、能复核、能沉淀的系统长期稳定。

这话听着有点像管理学鸡汤，但放在 AI 编程里，我觉得挺现实。

因为单 agent 最大的问题从来不是不聪明。

是不可控。

你让它 review 一个 PR，它可能看得很细，也可能漏掉关键路径。

你让它做深度研究，它可能找了很多资料，也可能把不可靠的来源混进去。

你让它修 bug，它可能修好了眼前的测试，又引入了另一个角落的问题。

不是它不努力。

是你不知道它中间到底怎么想，怎么查，怎么验证，怎么收口。

Workflow 解决的不是智商问题。

它解决的是过程问题。

这也是它跟 Skills、Subagents、MCP 最容易混，但又最应该分清楚的地方。

Skills 更像说明书。

你给 Claude Code 一份专业知识，告诉它这个场景该怎么做，输出格式是什么，踩坑点在哪里。

Subagents 更像临时工。

主 agent 把一块任务分出去，子 agent 做完再回来交差。

MCP 更像插座。

它把 GitHub、数据库、浏览器、本地文件这些外部资源接进来，让 Claude Code 能摸到更多东西。

Workflow 更像施工图加调度表。

它不只是告诉模型该做什么。

它规定阶段、预算、并行数量、验证方式、合并逻辑。

这个区别很关键。

Skills 还在 prompt 层。

Workflow 已经开始进入 program 层。

从 prompt 到 program，这个转变比新加一个命令大得多。

因为 prompt 天生有点虚。

模型理解了没有，按没按，跑到哪一步，你经常只能猜。

program 不一样。

它有 phase，有 agent，有 parallel，有 schema，有 log，有 budget。

你能看，能改，能复用，甚至能让另一个模型帮你审这个 workflow 脚本。

资料里那个 PR Review 的例子，我挺喜欢。

它不是直接放手让 Claude Code 改 PR。

它会先生成 context.md，把 PR 的上下文整理出来。

然后写一个 JavaScript workflow 脚本，大概三百行。

里面有 review，有 verify，有 synthesize。

review 阶段让多个 agent 从不同角度看代码。

verify 阶段用类似 3 vote majority confirmation 的方式，让几个 agent 对发现的问题交叉验证。

synthesize 阶段再把结果合成高、中、低优先级的问题列表。

这比一句 `帮我 review 这个 PR` 踏实很多。

更骚的是，你可以在 VS Code 里打开这个 JavaScript 脚本，让 Codex 或另一个助手先看一眼。

你觉得并行 agent 太多，就把数量从 6 个改成 3 个。

你觉得预算太大，就把 1M 改成 500k。

你觉得它应该先做安全审计，再做性能检查，也可以调整顺序。

然后再执行。

这才是我觉得比较健康的人机协作。

不是把方向盘直接扔给 AI，然后祈祷它别撞树。

而是让 AI 先写出驾驶路线，人看一眼，再让它开。

中间还有仪表盘。

你可以看 `/workflows`，看它跑到了哪一阶段，看 agent 怎么分布，看 token 花在哪。

这对信任感太重要了。

因为我们现在对 AI 编程最大的不安，不是它会不会写代码。

而是它写完之后，我到底敢不敢信。

Workflow 给出的答案不是你相信我。

而是你可以看我的过程。

这个思路，我觉得比单纯堆更强的模型更重要。

资料里还有一个让我挺有感觉的点，token 预算。

多 agent 听起来很爽，但如果没有预算控制，它就是 token 碎纸机。

你一激动开十几个 agent，每个 agent 都疯狂读上下文，账单到手能给你整不会。

所以 Workflow 里一个很现实的设计，是可以在任务里写预算。

比如 `workflow 100k`，或者早期资料里提到的 `ultrawork +500k`。

Claude Code 会根据这个预算规划 agent 数量、阶段深度和收敛方式。

这块其实非常关键。

很多人聊 AI 编程，只聊智能，不聊成本。

但真正跑项目的人都知道，成本不是小事。

如果一次 review 花 100 万 token，但结果只是帮你挑了几个命名问题，那就没必要。

如果一次 issue intelligence 花 50 万 token，却帮你把前 10 个 open issues 分类、排序、提取 maintainer 真正该看的风险点，那就可能很值。

Workflow 把这件事拿到了台面上。

不是盲目开干，而是带着预算开干。

这就很像你请团队做项目。

你不会只说，给我做好。

你会说，时间多少，预算多少，哪些必须做，哪些可以砍。

AI agent 也应该被这么管理。

这句话可能有点冷，但我觉得未来会越来越真。

不是每个任务都值得上 Opus。

不是每个步骤都值得深度推理。

真正厉害的系统，应该知道什么时候用便宜模型，什么时候用强模型，什么时候让多个 agent 互相验证，什么时候直接停。

Workflow 的价值就在这里。

它让 AI 编程从单次对话，走向可预算、可观察、可复用的任务系统。

那它适合什么场景？

我自己的判断是，凡是单 agent 容易卡住，但任务又可以拆开的地方，都适合。

比如代码审查。

一个 agent 看 PR，容易漏。

多个 agent 分别看正确性、并发、测试、安全、性能，再互相验证，结果会更稳。

比如 issue 分析。

开源项目里一堆 issue，人工一个个看很烦。

Workflow 可以先并行读，按 bug、feature、question、duplicate 分类，再让强模型判断 maintainer 优先级。

比如 bug 扫描。

你可以让多个 agent 从不同文件、不同风险角度并行找问题，再让验证 agent 过滤幻觉，再让 Opus 收口。

比如 deep research。

资料里提到的 deep research workflow 就很典型。

它不是让模型一口气搜完写答案，而是拆成 Scope、Search、Fetch、Verify、Synthesize。

搜索阶段可以用快模型。

抓取资料可以并行。

验证阶段可以让大量 agent 查证引用。

收口时再用强模型综合。

这对研究类内容非常有用。

因为我们做内容最怕什么？

最怕写得很顺，但事实是飘的。

一个可验证的 deep research workflow，至少能逼着模型把来源、原文引用、观点类型、可信度这些东西拆出来。

甚至内容生产也能用。

比如你不是让 Claude 一口气写一篇文章。

你可以让它先拆选题，再检索素材库，再找反方观点，再做事实核验，再生成几个角度，收口时才让写作 agent 动笔。

这不就是内容版 Workflow 吗？

我现在越写越觉得，Workflow 不只是开发者的事。

它更像是所有复杂脑力工作的下一层抽象。

以前我们学 prompt，是学怎么把一句话说清楚。

后来我们学 Skills，是学怎么把一种能力封装起来。

再后来我们学 MCP，是学怎么把外部世界接进来。

Workflow 再往前走一步，是学怎么把一组能力组织起来。

这个顺序很有意思。

先有资源，再有技能，再有组织。

像一个人慢慢长成公司。

当然，这东西不是魔法。

它有坑，而且坑还不小。

第一个坑，任务描述不清楚，Workflow 只会把混乱放大。

你自己都不知道要什么，它可以帮你生成十几个 agent，但十几个 agent 只是在并行误解你。

这比一个 agent 误解你还吓人。

第二个坑，预算不是装饰。

你写 500k，它就会按 500k 的思路规划。

你写 1M，它就可能铺得更开。

预算写得太小，结果可能浅。

预算写得太大，又可能浪费。

这需要人自己有判断。

第三个坑，能执行不等于可信。

Workflow 让过程更可见，但不代表过程天然正确。

agent 的判断依然可能错，验证 agent 也可能一起错。

所以我很喜欢资料里的 Human in the Loop 做法。

先写 workflow 脚本。

人审。

再跑。

跑完再看结果。

这个节奏虽然慢一点，但长期看更靠谱。

说真的，我现在对全自动一直有点警惕。

不是说全自动不酷。

而是很多时候，酷只是 demo 里的酷。

真正放到项目里，最重要的是可控、可回滚、可解释。

Workflow 如果用得好，反而不是让人消失。

它是把人从盯着模型每句话，提升到审一个流程、定一个预算、看一个结果。

人的角色变了。

从键盘工，变成调度者。

这才是我觉得它有意义的地方。

也许以后我们评价一个人会不会用 Claude Code，不是看他会不会写 prompt。

而是看他有没有自己的 workflow 资产。

比如一个稳定的 PR review workflow。

一个 bug audit workflow。

一个 deep research workflow。

一个 release checklist workflow。

一个内容选题到成稿的 workflow。

这些东西如果能沉淀在 `.claude/workflows/` 里，下次换项目还能拿出来改一改继续用，那它就不再是一次性的对话。

它开始变成资产。

prompt 是一次性的。

workflow 是可复用的。

这句话我越想越觉得有分量。

因为过去两年，我们很多人都在疯狂收藏 prompt。

但 prompt 收藏多了会有一个问题。

你真正用的时候，经常还是要改半天。

它更像灵感，不像系统。

Workflow 不一样。

如果它真能稳定下来，它可以像脚本、像模板、像 SOP、像自动化管道。

它可以被版本管理。

可以被 review。

可以被团队共享。

可以一点点变成熟。

这就是从会聊天的 AI，到会工作的 AI，中间最关键的一步。

我会怎么开始？

我的建议反而很保守。

不要一上来就让它全自动改生产项目。

先拿只读任务试。

比如 issue 分类、PR review、代码质量扫描、资料研究。

给它一个清楚的目标，一个明确预算，一个禁止直接修改的边界。

让它先写 workflow 脚本，不要立即执行。

你审一遍脚本，再跑。

跑完看 `/workflows` 状态，看 token 花在哪，看中间产物，看收口结论有没有证据。

如果结果稳定，再把脚本保存起来。

这个过程一开始可能有点笨。

甚至可能比你直接问 Claude Code 更慢。

但我觉得这恰恰是它有价值的地方。

真正值得沉淀的工作流，前几次都不会特别顺。

你要调阶段，调预算，调验证方式，调输出格式。

像调一个团队。

但一旦跑通，它就不只是帮你完成了一次任务。

它帮你留下了一套方法。

回到 Claude Code Workflow 这件事。

我现在的判断是，它不是一个新功能那么简单。

它是 AI 编程开始从个人能力，转向组织能力的信号。

以前我们问，一个模型能不能写代码。

后来我们问，一个 agent 能不能独立完成任务。

现在我们可能要问，一个系统能不能组织多个 agent，在预算内、可验证地完成复杂任务。

这个问题，才是真正的大问题。

因为未来的 AI 编程，可能不是你和一个超级程序员聊天。

而是你给一个小型工程组织下任务。

里面有负责搜索的，有负责实现的，有负责测试的，有负责审查的，有负责反驳的，有负责收口的。

你不再是一行一行催它写。

你是在设计它们怎么协作。

这事儿想想就有点赤鸡。

也有点危险。

但我还是很兴奋。

因为它把 AI 从一个聪明答案生成器，往真实生产系统的方向又推了一步。

而真正的生产系统，从来不是只靠聪明。

它靠分工，靠约束，靠验证，靠预算，靠复盘，靠沉淀。

Claude Code 的 Workflow，可能就是把这些工程世界里老掉牙但极其重要的东西，重新套回 AI agent 身上的一次尝试。

大时代啊，朋友们。

如果你已经在用 Claude Code，我建议这块一定要关注。

不要只看它能不能一键写完项目。

更要看它能不能把你每天重复做的复杂判断，沉淀成一个可以审、可以跑、可以复用的 workflow。

那才是真正会改变你工作方式的地方。
