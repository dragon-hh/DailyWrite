Claude Code 刚出了一个功能，叫 Workflow。
它把 Claude Code 从单兵作战，变成一个会自己编写流程、编排agent的超级系统。
## Claude Code 的 Workflow，不是新命令，是 AI 编程开始变形的地方

事情是这样的。

今天我连着看了三份 Claude Code Workflow 的资料，看完有点兴奋，也有点背后发凉。

因为它不是又多了一个斜杠命令，也不是 Claude Code 又会了一个小技巧。

它更像是 Claude Code 正在从一个会写代码的助手，慢慢变成一个会自己组织工程队的人。

---

一开始我对 Workflow 这个词没啥感觉。

因为"工作流"这个词说太多了，听着就像更复杂的流程图。

但 Claude Code 这里的 Workflow，不太一样。

它不是让你提前画好流程，然后让 Claude Code 照着做。

而是你用自然语言说出目标，Claude Code 先给自己生成一段 JavaScript 脚本，把任务拆成阶段，把不同阶段分给不同 agent，再让 runtime 去执行，再把结果收回来。

这一下味道就变了。

以前你是在跟一个模型聊天。

现在你是在让模型现场搭一个临时指挥系统。

---

有一个词反复出现：**Harness Engineering**。

你可以把它理解成给 agent 套上的工程轨道。

一个 agent 如果没有轨道，就像一个聪明但容易兴奋的实习生——你交给它一个大任务，它可能一口气往前冲，冲着冲着就偏了。

Harness 做的事，就是把它放进更可控的系统里。

什么时候搜索，什么时候分析，什么时候验证，什么时候停下来让人审——这些不是靠模型临场发挥，而是靠外面的结构来约束它。

以前这件事很专业，你得会写 LangGraph、AutoGen、CrewAI，得懂多 agent 调度，得设计状态机。说真的，这已经不是普通用户能玩的东西了。

但 Workflow 有意思的地方就在这里——它把 Harness 从人手写，变成 Claude Code 根据任务现场生成。

你说你想做什么，它说行，我先写一个小型指挥系统。

---

有一个很夸张的例子：Bun 从 Zig 迁移到 Rust，75 万行代码，99.8% 通过率，11 天完成。

这个数字我没法替人背书，但即使先不看结果，只看背后的思路，也够值得聊了。

因为真正有意思的不是 75 万行，也不是 11 天。

真正有意思的是，它不是让一个 Opus 从头到尾硬扛。

它会拆。

比如分类 GitHub Issues 的例子：它的做法是 10 个 Haiku 4.5 做广度分类，1 个 Opus 4.8 做收口判断。

便宜模型干脏活，强模型做决策。

这就很像真实公司——你不会让 CTO 一个人读完所有客服工单，也不会让实习生拍板架构方向。

AI 编程走到这一步，终于开始有一点组织结构的味道了。

---

这也是 Workflow 跟 Skills、Subagents、MCP 最容易混，但最应该分清楚的地方。

Skills 更像说明书——你告诉模型这个场景该怎么做。

Subagents 更像临时工——主 agent 把任务分出去，子 agent 做完再交差。

MCP 更像插座——把 GitHub、数据库、文件这些外部资源接进来。

**Workflow 更像施工图加调度表。**

它规定阶段、预算、并行数量、验证方式、合并逻辑。

这个区别很关键。

Skills 还在 prompt 层。Workflow 已经进入 program 层。

prompt 天生有点虚——模型理解了没有，按没按，你经常只能猜。

program 不一样，它有 phase，有 agent，有 schema，有 log，有 budget。你能看，能改，能复用。

---

我看到一个 PR Review 的例子，挺喜欢。

它不是直接放手让 Claude Code 改 PR。

它先生成 context.md，整理 PR 上下文，再写一个大概三百行的 JavaScript workflow 脚本。

里面有 review、verify、synthesize 三个阶段。

review 阶段让多个 agent 从不同角度看代码，verify 阶段用类似 3 vote majority 的方式交叉验证，synthesize 阶段再把结果合成高中低优先级列表。

更重要的是，你可以在 VS Code 里打开这个脚本，觉得并行 agent 太多，就把 6 个改成 3 个，觉得预算太大，就从 1M 改成 500k，然后再执行。

这才是比较健康的人机协作——不是把方向盘直接扔给 AI 然后祈祷它别撞树，而是让 AI 先写出驾驶路线，人看一眼，再让它开。

---

还有一个点让我挺有感觉：**token 预算**。

多 agent 听起来很爽，但没有预算控制，它就是 token 碎纸机。

你一激动开十几个 agent，每个都疯狂读上下文，账单到手能给你整不会。

所以 Workflow 里一个很关键的设计，是可以直接在任务里写预算，比如 `workflow 100k`。

Claude Code 会根据这个预算规划 agent 数量、阶段深度和收敛方式。

这其实非常关键。很多人聊 AI 编程只聊智能，不聊成本。但真正跑项目的人都知道，成本不是小事。

不是每个任务都值得上 Opus，不是每个步骤都值得深度推理。真正厉害的系统，应该知道什么时候用便宜模型，什么时候用强模型，什么时候直接停。

---

那 Workflow 适合什么场景？

我自己的判断是，凡是单 agent 容易卡住，但任务又可以拆开的地方，都适合。

代码审查、issue 分析、bug 扫描、deep research 就很典型——它不是让模型一口气搜完写答案，而是拆成 Scope、Search、Fetch、Verify、Synthesize，搜索阶段用快模型，抓取资料可以并行，收口时再用强模型综合。

甚至内容生产也能用——你不是让 Claude 一口气写一篇文章，而是让它先拆选题，再检索素材，再找反方观点，再做事实核验，收口时才让写作 agent 动笔。

这不就是内容版 Workflow 吗？

---

当然，它有坑，而且坑不小。

**第一个坑**，任务描述不清楚，Workflow 只会把混乱放大。十几个 agent 并行误解你，比一个 agent 误解你还吓人。

**第二个坑**，预算不是装饰。写太小结果浅，写太大可能浪费，这需要人自己有判断。

**第三个坑**，能执行不等于可信。Workflow 让过程更可见，但不代表过程天然正确。agent 的判断依然可能错，验证 agent 也可能一起错。

所以我很喜欢 Human in the Loop 这个做法——先写 workflow 脚本，人审，再跑，跑完再看结果。

这个节奏虽然慢一点，但长期更靠谱。

---

说真的，Workflow 如果用得好，反而不是让人消失。

它是把人从盯着模型每句话，提升到审一个流程、定一个预算、看一个结果。

人的角色变了——从键盘工，变成调度者。

也许以后我们评价一个人会不会用 Claude Code，不是看他会不会写 prompt，而是看他有没有自己的 workflow 资产。

一个稳定的 PR review workflow，一个 bug audit workflow，一个 deep research workflow……

这些东西如果能沉淀在 `.claude/workflows/` 里，下次换项目还能拿出来改改继续用，它就不再是一次性的对话。

**它开始变成资产。**

prompt 是一次性的，workflow 是可复用的。

这句话我越想越觉得有分量。

---

我的建议反而很保守。

不要一上来就让它全自动改生产项目。

先拿只读任务试——issue 分类、PR review、代码质量扫描。

给它清楚的目标、明确预算、禁止直接修改的边界。

让它先写 workflow 脚本，不要立即执行。你审一遍，再跑，跑完看中间产物、看收口结论有没有证据。

结果稳定了，再把脚本保存起来。

像调一个团队。前几次不会特别顺，但一旦跑通，它帮你留下的不只是一次任务的结果，而是一套方法。

---

回到 Claude Code Workflow 这件事，我现在的判断是——

它不是一个新功能那么简单。

它是 AI 编程开始从个人能力，转向组织能力的信号。

以前我们问，一个模型能不能写代码。

后来我们问，一个 agent 能不能独立完成任务。

现在我们要问的是：**一个系统能不能组织多个 agent，在预算内、可验证地完成复杂任务。**

这个问题，才是真正的大问题。

因为真正的生产系统，从来不是只靠聪明。

它靠分工，靠约束，靠验证，靠预算，靠沉淀。

大时代啊，朋友们。
