
标题：只剩2%额度如何用Codex
Codex高手不会说的技巧,/goal指令

文案：
Codex 额度快用完的时候，
别再一条一条问了，
最后那点额度
最适合
拿来跑一个完整目标。

最近 Codex 的额度
消耗得非常快，
没跑几个任务，
额度就快没了。

所以今天
我给大家分享一个命令，
可能能帮你
省掉一个 Pro 订阅的 token。

就是这个 /goal 命令。


但是在讲 /goal 之前，
我得先给大家
讲一个 Codex 的机制，
我把它叫「透支机制」。

很多人不知道，
哪怕你的 Codex 额度
已经快见底了，
比如只剩 2% 了，
只要你当前这个任务
还没跑完，
Codex 不会中途给你停掉。

这个机制单独用，
好像没啥特别的。
但是跟 /goal 命令结合起来，
就很有意思了。


那 /goal 命令是什么？

普通指令的模式是，
一问一答，一步一步来。

/goal 模式是：
你给它一个目标，
它会自己规划，执行，验证，
发现不对就自己调整，
然后一轮轮迭代，
直到这个目标达成才停下来。


一个 /goal 命令，
可以顶你过去发的
几条甚至几十条指令。

所以加上透支机制，
你在只剩很少额度的时候，
发出一个 /goal 指令，
Codex 会一路给你跑到底，
把整个目标完成才停。

这一下，能干多少事，
你想想看。



好，那 /goal 怎么用？

我发现很多人
写出来的 /goal 指令质量很差，
就是随手写了一句话发进去，
然后 Codex 自己发挥，
效果玄学，
有时候做出来的东西
跟你想的差很远。

这不是 /goal 的问题，
是你的指令写法有问题。

重点就是三部分。

第一，目标终态。

就是你希望这件事做完的时候，
最终的结果是什么样的。
注意，不是「让它做什么」，
而是「做完之后是什么状态」。
这两个看起来差不多，
其实差很远。
你把终态描述得越清楚，
它跑的方向就越准。



第二，约束边界。

哪些东西不能动，
必须用哪个技术栈，
代码风格有没有要求，
兼容性方面有没有限制。
你不说，它会自己决定，
然后可能会跑偏。
尤其是「不能用某个依赖」
「不能改某个接口的签名」
这种负向约束，
一定要显式写出来，
不然它会自己猜。



第三，验收标准。

怎么算做完了。
测试通过算完？
还是在浏览器里
能看到某个效果算完？

这个验收标准非常关键，
因为 /goal 的核心
就是 Codex 要能自己判断
「我完成了没有」，
才能驱动它的迭代循环。
没有这个，
它可能跑到一半
就自认为完成了，
或者一直在兜圈子，
不知道什么时候该停。



其实 /goal 的指令
也不需要我们自己去想，
直接让 Codex
基于你的需求，
写一个 /goal 指令，
然后你再拿着这个 /goal 指令，
新开线程去跑。

/goal 命令我自己用下来，
是真的省了不少来回，
尤其到月底
token 快耗尽的那几天，
一个 /goal 加上透支机制，
基本上把 Codex 的额度拉满了。
