你有没有这样的困惑，作为一个非专业程序员，但是我想写一个比较专业、完整的软件或小程序
有没有解决办法？
所以今天给大家介绍一套最近在开发圈很火的顶级开发工作流。
目前在 GitHub 上已经超过16万颗星。它是一整套工程级开发skill，
让你能从一个模糊的想法开始，形成完整的需求，拆分合适的任务，高效代码开发和测试，最终沉淀出完整的系统和文档。
今天我把这一套 skill 中最核心，最值得学习的5个 skill 给大家拆解一下。
不仅仅适用于代码开发，任何AI参与的相关的工作都可以用得上。
第一步 聊需求，grill-with-doc，通过不断的追问，帮你梳理清你到底想要做什么，并把关键的想法、专业术语沉淀到文档中，作为后续开发的依据。
这一步是非常痛苦的，因为它强制要求你停下来，先把需求想清楚，先把问题想清楚，再真正开发，比如我这里给codex了一个最初的需求文档，它足足问了我25个问题，
从核心产品边界、技术架构、数据存储、MVP范围，这些关键问题在它的追问下，我才慢慢确定下来。
AI赋予我们强大的代码开发能力，但也导致我们经常代码写完了，才想起之前产品边界没有想清楚，产品功能没有想清楚
这一步虽然痛苦，但是值得花心思。
第二步 to-prd ，把我们刚才的讨论结果，生成正式的需求文档
它会写清楚：
用户到底遇到什么问题。
我们要给他什么结果。
测试要从哪个边界切进去。
目前已经做了哪些技术上的决策

第三步 `to-issues` 它负责把一个大需求（PRD）拆成多个 agent 可以独立完成的小任务。

这里面有一个术语叫 纵向切片。

听起来专业，其实特别好懂。

比如：

假设你要做一个外卖点餐小程序。

错误拆法是：

第一个 issue 做菜单页面。

第二个 issue 做购物车。

第三个 issue 做下单接口。

第四个 issue 做支付。

第五个 issue 做订单通知。

这几个任务听起来都合理，但单独完成任何一个，用户都无法完成一次点餐。

纵向切片会这样拆：

第一个 issue，只支持一个固定套餐，让用户能看到商品、点一下购买，并生成一个订单。

第二个 issue，在这个闭环上补购物车，让用户可以选择数量。

第三个 issue，接入真实支付。

第四个 issue，补订单状态，让用户知道商家是否接单、骑手是否出发。

第五个 issue，再扩展到多商家、多菜品、优惠券。

每个 issue 都能单独跑、单独测、单独 review。

这才适合 AI agent 并行工作。

因为 agent 最怕的不是任务大。

是任务边界不清。

第四步 `implement` 实现，它会基于每个issue完成代码开发
这个skill又会调用 tdd、code-review 这两个skill
具体的思路是测试驱动开发，加代码审查，完成工作后会自动提交分支。
code-review我单独说一下，它有个双轴审查（Two-axis review）很有意思：。
它会把一次代码审查拆成两条线并行看：
1. Standards：这代码是否符合项目自己的工程规范？
2. Spec：这代码是否真的实现了原本 issue 或 PRD 要求的东西？

为什么要分两轴？
因为这两类问题经常不同：
```
代码可以写得很干净，但实现错需求。
代码可以实现了需求，但违反项目架构规则。
```

最后总结一下 一个完整的开发流程应该是
第一步 通过追问澄清需求
第二步 基于讨论结果生成正式PRD文档
第三步 将PRD文档拆分成可独立运行的子任务
第四步  多线程并行实现，完成代码开发
